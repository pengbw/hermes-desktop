## R1：项目模板增加"自定义"选项

### 原始需求

> 工作室中创建项目时候模板中添加一个自定义、自定义的话创建后，没有人员角色、流程

### 用户补充

> 自定义的项目模板创建后应该有工作空间规则

### 现状分析

- 当前 `NewProjectModal.tsx` 只有模板列表，没有"自定义"选项
- 创建项目必须选择模板（`create_project_from_template`），没有无模板创建路径
- 模板中包含 `projectRule` 和 `projectGuidelines`（工作空间规则），如软件开发模板的 `projectRule: "遵循敏捷开发流程..."`

### 详细需求

**交互流程**：

1. 新建项目弹窗的模板列表顶部增加"✨ 自定义"卡片
2. 选择"自定义"后，项目名称、描述、图标等字段正常填写
3. 点击创建 → 调用新的 `create_empty_project` 命令
4. 创建后的项目：
   - ✅ 有工作空间规则（`project_rule` / `project_guidelines`）—— 使用通用默认规则
   - ❌ 无成员、无角色、无流程
5. 用户进入项目后，通过"添加角色"和"流程设计器"手动配置

**默认工作空间规则**（自定义项目使用，与模板规则不同，体现"自定义"特性）：

```
project_rule: "自定义项目，由项目创建者自主定义协作规范与交付标准。"
project_guidelines: "1. 自行定义角色职责与工作流程\n2. 明确每个任务的验收标准\n3. 产出物需经过审核确认\n4. 保持团队协作和信息同步"
```

**数据模型**：

- 无新增表
- `projects` 表正常插入，`project_rule` 和 `project_guidelines` 使用默认值
- `project_members` 和 `project_workflows` 为空

**前端变更**：

- `NewProjectModal.tsx`：模板列表增加"自定义"卡片
- 选择自定义时隐藏模板预览

**后端变更**：

- 新增 `create_empty_project` 命令，创建 project 记录并设置默认工作空间规则，不创建成员和工作流

## R2：主流程标记不可删除 + 被绑定流程不可删除

### 原始需求

> 选择模板生产项目、有人员角色、流程、但生成的这条流程为主流程、不可删除

### 用户补充

> 主流程不能删、被绑定的流程也不能删

### 现状分析

- 当前 `project_workflows` 表没有"主流程"概念
- 流程设计器中所有工作流节点都可以删除（右键 → 删除）
- 模板生成的流程和用户手动添加的流程没有区分
- 任务分配时可以关联流程（R5），被任务绑定的流程也不应被删除

### 详细需求

**数据模型**：

- `project_workflows` 表新增字段：`is_primary BOOLEAN NOT NULL DEFAULT 0`
- 模板创建项目时，所有工作流的 `is_primary = 1`
- 用户手动添加的工作流 `is_primary = 0`

**不可删除规则**：

1. **主流程不可删除**：模板生成的流程标记为主流程，任何连线/节点都不可删除
2. **被绑定的流程不可删除**：如果有任务（`project_tasks.workflow_group_id`）关联了该流程组，则该流程组不可删除
   - 需要先删除或解绑所有关联的任务，才能删除该流程组

**交互规则**：

1. 流程设计器中，主流程的连线/节点显示"🔒 主流程"标识
2. 主流程的连线不可删除（删除按钮灰显或隐藏）
3. 被绑定的流程组在流程列表中显示"📎 已绑定"标识，删除按钮灰显
4. 主流程的节点属性可编辑（产物类型、流转方式），但节点本身不可删除
5. 流程列表中主流程标注"主流程"标签

**前端变更**：

- `WorkflowDesigner.tsx`：主流程连线/节点增加标识，禁用删除
- `ProjectDetail.tsx`：流程列表显示主流程标签和绑定状态

**后端变更**：

- 数据库迁移：`ALTER TABLE project_workflows ADD COLUMN is_primary BOOLEAN NOT NULL DEFAULT 0`
- `create_project_from_template`：设置 `is_primary = 1`
- `remove_project_workflow` / `delete_workflow_group`：
  - 检查 `is_primary`，主流程返回错误："主流程不可删除"
  - 检查是否有任务绑定该流程组，有则返回错误："该流程已被任务绑定，请先解绑任务"
- `list_project_workflows`：返回 `is_primary` 字段

## R3：项目支持多流程、可添加/编辑流程

### 原始需求

> 一个项目中可以有多个流程、用户可以在流程列表中添加流程、点击编辑、可以编辑流程、流程的其他功能不变

### 用户补充

> R3 多流程：如果 Hermes Agent 支持子流程，我们就添加进去

### Hermes Agent 子流程能力分析

- Hermes Agent 的 `delegate_task` 支持嵌套委派，但有深度限制（MAX_DEPTH=2）
- 当前不支持子流程之间的通信和状态共享
- Hermes Agent 正在规划 Multi-Agent Architecture（Issue #344），未来可能支持结构化工作流 DAG
- **结论**：当前阶段先实现独立并行流程，预留子流程扩展接口，待 Hermes Agent 多 Agent 架构成熟后再支持

### 现状分析

- 当前项目已支持多流程（`project_workflows` 表可存储多条记录）
- 流程设计器已支持添加/编辑/删除连线
- 但缺少"流程分组"概念——所有工作流混在一起显示

### 详细需求

**数据模型**：

- 新增 `project_workflow_groups` 表：
  ```sql
  CREATE TABLE project_workflow_groups (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    name TEXT NOT NULL DEFAULT '默认流程',
    is_primary BOOLEAN NOT NULL DEFAULT 0,
    sort_order INTEGER NOT NULL DEFAULT 0,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE
  );
  ```
- `project_workflows` 表新增字段：`group_id TEXT`，关联流程组
- 预留子流程扩展：`project_workflow_groups` 表增加 `parent_group_id TEXT` 字段（当前为 NULL，未来支持子流程嵌套）

**交互流程**：

1. 项目详情页"流程"标签下，顶部显示流程组列表（横向标签页）
2. 每个流程组标签右侧有"编辑名称"和"删除"按钮（主流程和被绑定流程不可删除，见 R2）
3. 右上角"➕ 添加流程"按钮 → 弹出输入流程名称 → 创建新流程组
4. 点击流程组标签 → 切换到该流程的设计器视图
5. 设计器中只显示当前流程组的工作流连线

**前端变更**：

- `ProjectDetail.tsx`：流程标签页增加流程组列表
- `WorkflowDesigner.tsx`：接收 `groupId` 参数，只加载该组的工作流

**后端变更**：

- 新增 CRUD 命令：`create_workflow_group`、`update_workflow_group`、`delete_workflow_group`、`list_workflow_groups`
- 修改 `list_project_workflows`：支持按 `group_id` 过滤
- 修改 `add_project_workflow`：需要指定 `group_id`

## R4：创建任务不再自动触发流程

### 原始需求

> 添加任务不在自动触发流程、创建后任务都是待办状态

### 现状分析

- 当前 `create_project_task` 有 `assignee` 时立即调用 `do_dispatch_task`
- `do_dispatch_task` 会：① 更新任务状态为 running ② 如果是起始角色则触发 `start_workflow_run` ③ 调用 `auto_delegate_chat`
- 前端 `TaskBoard.tsx` 创建任务默认 `status = "todo"`
- 前端 `TaskManagement.tsx` 创建任务默认 `status = "todo"`

### 详细需求

**核心变更**：创建任务只是创建记录，不触发任何工作流或派发

**交互规则**：

1. 创建任务后，状态固定为 `todo`（待办）
2. 即使指定了 `assignee`，也不自动派发
3. 任务需要通过 R5 的"分配"操作才会开始执行

**后端变更**：

- `create_project_task`：移除自动调用 `do_dispatch_task` 的逻辑
- 创建任务时只 INSERT 记录，不触发任何后续操作
- 保留 `do_dispatch_task` 函数，但改为由 R5 的"分配"操作显式调用

**前端变更**：

- 创建任务表单移除 `assignee` 字段（分配在 R5 的弹窗中完成）
- 创建后任务出现在"待办"列

## R5：待办任务增加"分配"按钮和弹窗

### 原始需求

> 在任务列表中、待办任务、有分配任务的按钮、点击分配按钮后、弹出分配任务的弹窗、用户可以在弹窗中选择任务受理人、以及项目中的流程、点击确认分配后，按照选择的流程去执行、整个流程结束、任务就完成、如果没有选择流程，就受理人直接去完成任务、受理人完成了 任务就完成、在这个过程中、每个角色要收到任务后、和完成后都要在项目动态中展现出来

### 用户补充

> 1. 任务分配时，如果选流程则受理角色默认为流程起始角色、不选流程则可以选择受理人
> 2. 无流程模式：受理人完成后需要用户确认，也是和审批一样的方式

### 现状分析

- 当前有"派发"按钮（`dispatch_task_to_role`），但只选择角色，不选择流程
- 派发后自动触发工作流（如果角色是起始角色）
- 没有让用户选择"按哪个流程执行"的选项
- 项目动态（`project_activities`）已有记录机制，但角色收到任务和完成任务时的记录不完整

### 详细需求

**交互流程**：

1. 待办任务（status = `todo`）卡片上显示"📋 分配"按钮
2. 点击"分配" → 弹出分配弹窗，包含：
   - **流程选择**（优先）：下拉列表，显示项目中的所有流程组（含"不使用流程"选项）
   - **受理人选择**：下拉列表，显示项目中的所有角色成员
     - ⚡ 如果选择了流程 → 受理人自动锁定为该流程的起始角色，不可更改
     - 🔧 如果选择"不使用流程" → 受理人可自由选择
   - **任务说明**：文本框，可给受理人附加说明（可选）
3. 点击"确认分配"：
   - 如果选择了流程 → 按该流程执行，受理人为流程起始角色
   - 如果选择"不使用流程" → 受理人直接执行任务
4. 任务状态变为 `running`
5. 流程执行过程中，每个角色收到任务和完成任务时，在项目动态中记录

**两种执行模式**：

| 模式   | 受理人确定方式           | 任务完成条件                                          |
| ------ | ------------------------ | ----------------------------------------------------- |
| 有流程 | 流程起始角色（自动锁定） | 整个流程完成后任务 `done`                             |
| 无流程 | 用户自由选择             | 受理人完成后 → 提交产物待审核 → 用户确认后任务 `done` |

**无流程模式的确认机制**（与审批相同）：

1. 受理人完成工作后，产物状态变为 `submitted`（待审核）
2. 用户在"待办"面板（R7）中审核确认
3. 用户确认通过 → 任务状态变为 `done`
4. 用户驳回 → 受理人继续修改

**数据模型**：

- `project_tasks` 表新增字段：`workflow_group_id TEXT`（关联的流程组）
- 分配记录：复用 `task_dispatches` 表，增加 `workflow_group_id` 字段

**后端变更**：

- 新增 `assign_task` 命令：
  ```rust
  async fn assign_task(
    app: AppHandle,
    task_id: String,
    assignee: String,           // 受理人角色 ID
    workflow_group_id: Option<String>,  // 流程组 ID（None = 无流程）
    message: Option<String>,    // 附加说明
  ) -> Result<(), String>
  ```
- 逻辑：
  1. 更新任务 `assignee`、`status = running`、`workflow_group_id`
  2. 如果有 `workflow_group_id` → 查找该流程组的起始角色 → 触发 `start_workflow_run`
  3. 如果无 `workflow_group_id` → 直接 `auto_delegate_chat`
  4. 记录活动：`task_assigned`（角色收到任务）
- 新增 `get_workflow_start_role` 命令：返回流程组的起始角色 ID（前端用于自动锁定受理人）
- `auto_delegate_chat` 完成时（无流程模式）：产物状态变为 `submitted`，等待用户确认
- 工作流完成时（有流程模式）：记录活动 `task_step_completed`，标记任务 `done`

**前端变更**：

- `TaskBoard.tsx`：待办任务卡片增加"📋 分配"按钮
- `TaskManagement.tsx`：待办任务行增加"📋 分配"按钮
- 新增 `AssignTaskModal` 组件：分配弹窗
  - 流程选择联动：选择流程后自动填充受理人为起始角色
  - 不选流程时受理人下拉可编辑

**项目动态记录**：

- 角色收到任务：`{ type: "task_assigned", role: "PM", detail: "收到任务：创建公司主页" }`
- 角色完成工作：`{ type: "task_step_completed", role: "PM", detail: "完成了需求文档" }`
- 产物提交审批：`{ type: "artifact_submitted", role: "PM", detail: "提交了需求文档待审批" }`
- 产物审批通过：`{ type: "artifact_approved", role: "PM", detail: "需求文档审批通过" }`

## R6：进行中任务增加"进度查询"按钮

### 原始需求

> 任务在进行中时候、在任务卡片上要有进度的按钮、点击按钮后，可以看到任务执行的进度、以及任务执行的详细信息

### 现状分析

- 当前任务卡片没有进度查询功能
- `WorkflowRunPanel.tsx` 已有工作流运行状态展示（步骤列表、状态）
- `workflow_run_steps` 表记录了每个步骤的状态
- 但没有将任务与工作流运行关联起来的查询入口

### 详细需求

**交互流程**：

1. 进行中任务（status = `running`）卡片上显示"📊 进度"按钮
2. 点击"进度" → 弹出进度面板/弹窗，显示：
   - **任务基本信息**：标题、受理人、开始时间
   - **流程进度**：如果关联了流程，显示流程步骤进度条
     - 每个步骤：角色名 + 产物类型 + 状态（✅已完成 / 🔄进行中 / ⏳待处理 / 🔒待审批）
   - **执行详情**：
     - 当前正在工作的角色
     - 已完成的产物列表（可点击查看）
     - 待审批的产物（可点击审批）
   - **项目动态**：该任务相关的最近活动记录

**数据来源**：

- 任务信息：`project_tasks`
- 流程进度：`workflow_runs` + `workflow_run_steps`
- 产物列表：`project_artifacts`
- 活动记录：`project_activities`（按 `task_id` 或 `project_id` 过滤）

**前端变更**：

- `TaskBoard.tsx`：进行中任务卡片增加"📊 进度"按钮
- `TaskManagement.tsx`：进行中任务行增加"📊 进度"按钮
- 新增 `TaskProgressModal` 组件：进度弹窗

**后端变更**：

- 新增 `get_task_progress` 命令：返回任务的完整进度信息
  ```rust
  struct TaskProgress {
    task: ProjectTask,
    workflow_run: Option<WorkflowRunDetail>,
    artifacts: Vec<ProjectArtifact>,
    activities: Vec<ProjectActivity>,
  }
  ```

## R7：任务页签增加"待办"审核面板

### 原始需求

> 产物需要审核时候、在项目的窗口自动弹出窗口、里边是产物的列表、下方是审核的描述框、在下方是通过和驳回的按钮，窗口需要主动关闭才能关闭。文本产物点击可以看看，其他文件提示"文件夹中浏览"

### 用户补充

> 1. 审核的产物审核窗口在没有审核的情况下关闭窗口了，所以我们应该要在任务的页签中添加待办、左边显示任务列表、右边显示所有需要审核的产物、待办的内容要有任务信息、角色等描述、以及对应的产物
> 2. 审核窗口弹出采用前端监听的方式
> 3. 多个待审核产物显示一个列表

### 现状分析

- 当前审批操作在产物列表中手动点击"通过/驳回"按钮
- 审核弹窗关闭后，待审核产物没有统一的查看入口
- 没有自动弹出审核窗口的机制
- 产物内容查看功能已有（MarkdownRenderer），但只支持文本

### 详细需求

**整体设计**：将审核功能从"弹窗"改为"任务页签中的待办面板"，同时保留前端监听自动弹出提醒

**A. 任务页签增加"待办"子标签**：

1. 项目详情页的任务标签下，增加"待办"子标签页
2. 待办面板布局：
   - **左侧**：待审核任务列表
     - 每个任务卡片显示：任务标题、受理人角色、任务状态、创建时间
     - 点击任务 → 右侧显示该任务的待审核产物
   - **右侧**：待审核产物详情
     - 产物列表（多个待审核产物显示为一个列表）
     - 每个产物显示：产物标题、类型、提交角色、提交时间
     - 产物预览区：
       - 文本产物（md/txt/json 等）：点击后内嵌预览（使用 MarkdownRenderer）
       - 其他文件：显示"📂 在文件夹中浏览"按钮，点击打开系统文件管理器
     - 审核描述框：文本输入框，填写审核意见
     - 操作按钮：
       - ✅ 通过：调用 `approve_project_artifact`
       - ❌ 驳回：调用 `reject_project_artifact`（审核意见必填）

**B. 前端监听自动弹出审核提醒**：

## R8：后端推送数据自动刷新（含防抖）

### 原始需求

> 项目页面中的任务状态、产物、人员状态、要从后端推数据自动刷新数据、默认进入页面则是前端主动加载数据

### 用户补充

> 推送频率需要防抖/节流，短时间内多次状态变更需要合并推送

### 现状分析

- 当前前端数据刷新方式：用户操作后手动调用 `refreshTasks()`、`refreshArtifacts()` 等
- 后端有 Tauri 事件系统（`app.emit`），但只用于特定场景
- 没有防抖/节流机制

### 详细需求

**架构设计**：

```
后端数据变更 → 防抖队列（500ms） → app.emit("project_data_changed", payload) → 前端监听 → 按需刷新
```

**后端防抖机制**：

1. 后端维护一个按 `project_id` 分组的事件队列
2. 短时间（500ms）内同一项目的多次数据变更合并为一次推送
3. 合并后的推送包含所有变更的数据类型，前端一次性刷新

**后端推送事件**：

| 事件名                    | 触发时机                   | Payload                                                                       |
| ------------------------- | -------------------------- | ----------------------------------------------------------------------------- |
| `project_data_changed`    | 任何项目数据变更（防抖后） | `{ projectId, changes: ["tasks", "artifacts", "members", "workflow_steps"] }` |
| `artifact_status_changed` | 产物状态变更（即时）       | `{ projectId, artifactId, oldStatus, newStatus }`                             |
| `task_status_changed`     | 任务状态变更（即时）       | `{ projectId, taskId, oldStatus, newStatus }`                                 |
| `workflow_step_changed`   | 工作流步骤变更（即时）     | `{ projectId, runId, stepIndex, status }`                                     |
| `member_status_changed`   | 人员状态变更（即时）       | `{ projectId, roleId, status }`                                               |

**防抖实现**：

```rust
use std::collections::HashMap;
use std::sync::Mutex;
use tokio::sync::mpsc;

struct DebouncedEmitter {
    pending: Mutex<HashMap<String, Vec<String>>>,  // project_id → changed data types
    debounce_ms: u64,
}
```

- 后端收到数据变更请求 → 将 `dataType` 加入 `pending[project_id]` → 启动/重置 500ms 定时器
- 定时器到期 → 合并所有 `dataType` → `app.emit("project_data_changed", payload)` → 清空 `pending[project_id]`
- `artifact_status_changed` 等即时事件不经过防抖队列，直接推送

**前端监听**：

1. 进入项目详情页时：
   - 主动加载所有数据（现有逻辑不变）
   - 注册事件监听器
2. 收到 `project_data_changed` 事件时：
   - 根据 `changes` 数组，只刷新对应的数据
   - 例如 `changes: ["tasks", "artifacts"]` → 只刷新任务和产物
3. 收到即时事件（如 `artifact_status_changed`）时：
   - 用于触发特定 UI 行为（如弹出审核提醒）
4. 离开项目详情页时：
   - 注销所有事件监听器

**后端变更**：

- 新增 `DebouncedEmitter` 模块
- 在以下操作后 emit 事件：
  - `auto_delegate_chat` 完成 → `task_status_changed`、`artifact_status_changed`、`member_status_changed`
  - `approve_project_artifact` → `artifact_status_changed`、`workflow_step_changed`
  - `reject_project_artifact` → `artifact_status_changed`
  - `trigger_workflow_execution` → `workflow_step_changed`
  - `assign_task` → `task_status_changed`
- 所有变更同时加入防抖队列，统一推送 `project_data_changed`

**前端变更**：

- `ProjectDetail.tsx`：增加 `useEffect` 注册/注销事件监听
- 收到事件后调用对应的 refresh 函数
- `TauriEvents.ts`：新增项目数据变更事件监听

## R9：虚拟办公人物状态与实际数据联动（含状态标签）

### 原始需求

> 我们虚拟办公的场景要和实际数据结合起来、虚拟办公的人员状态要根据实际情况显示、人物在空闲时间、可以走动、去沙发上坐坐、到书架区走在、可以随机、在人员忙碌的时候要回到工位、状态开始显示为忙碌

### 用户补充

### 详细需求

3. 标签位置：角色头顶偏上
4. 标签样式：半透明背景，圆角，小字体

1. 依赖 R8 的后端推送

## R10：产物产出角色绑定重新设计

### 用户补充

> 产物产出角色、现在绑定有些问题需要重新设计

### 现状分析

- 当前 `project_artifacts` 表的 `role_id` 字段记录产物所属角色
- 问题 1：`add_project_member` 时自动创建 `artifact_type = 'auto'` 的产物，role_id 正确
- 问题 2：`trigger_workflow_execution` 创建产物时，`role_id` 设置为 `to_role_id`（目标角色），这是正确的
- 问题 3：`record_chat_files` 在角色聊天完成后更新文件记录的 `role_id`，但之前有空 role_id 的 bug（已修复）
- 问题 4：产物与工作流步骤的关联不明确——同一角色可能有多个产物（不同 artifact_type），无法区分哪个产物属于哪个工作流步骤
- 问题 5：产物与任务的关联——`task_id` 字段存在但很多地方传空字符串

### 详细需求

**核心问题**：产物需要明确关联到"哪个任务的哪个工作流步骤"，而不仅仅是"哪个角色"

**数据模型变更**：

- `project_artifacts` 表新增字段：
  - `workflow_run_id TEXT`：关联的工作流运行 ID
  - `step_index INTEGER`：关联的工作流步骤索引
- 修改现有字段：
  - `task_id TEXT NOT NULL DEFAULT ''` → 创建产物时必须关联任务 ID

**产物创建规则**：

1. **工作流触发创建产物**：`trigger_workflow_execution` 创建产物时
   - `role_id = to_role_id`（目标角色，不变）
   - `task_id`：从工作流运行中获取关联的任务 ID
   - `workflow_run_id`：当前工作流运行 ID
   - `step_index`：当前步骤索引
2. **添加成员自动创建产物**：`add_project_member` 创建产物时
   - `role_id`：成员角色 ID（不变）
   - `task_id = ''`（无任务关联）
   - `workflow_run_id = NULL`
   - `step_index = NULL`
3. **角色聊天产出文件**：`record_chat_files` 更新文件记录时
   - `role_id`：当前聊天角色（不变）
   - `task_id`：从聊天上下文中获取
   - 不修改 `workflow_run_id` 和 `step_index`（文件可能不属于特定步骤）

**产物查询优化**：

- 按角色查询产物：`SELECT * FROM project_artifacts WHERE project_id = ? AND role_id = ?`
- 按任务查询产物：`SELECT * FROM project_artifacts WHERE project_id = ? AND task_id = ?`
- 按工作流步骤查询产物：`SELECT * FROM project_artifacts WHERE workflow_run_id = ? AND step_index = ?`
- 查询角色当前活跃产物：`SELECT * FROM project_artifacts WHERE project_id = ? AND role_id = ? AND status IN ('in_progress', 'pending')`

**后端变更**：

- 数据库迁移：新增 `workflow_run_id` 和 `step_index` 字段
- `trigger_workflow_execution`：创建产物时填充 `task_id`、`workflow_run_id`、`step_index`
- `start_workflow_run`：关联任务 ID 到工作流运行
- `list_project_artifacts`：返回新字段

**前端变更**：

- 产物列表展示：显示产物所属任务和工作流步骤
- 角色状态判断：基于 `role_id + status` 查询，更精确
